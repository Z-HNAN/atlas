## Context

- 需要在现有仓库中新增一个基于 React 的 Garfish 父容器应用。
- 父容器负责子应用注册、路由与统一导航（顶部 Tab + Home）。
- 子应用配置需要可视化录入，优先采用本地存储以降低后端依赖。

## Goals / Non-Goals

**Goals:**
- 提供父容器基础布局与路由骨架（应用创建于仓库根目录）。
- 主页作为导航页面，以卡片网格展示已添加的子应用，类似浏览器书签。
- 主页显示【+】块，点击进入添加子应用表单（最少字段：name、url）。
- 点击子应用块进入对应子应用，顶部显示该子应用 Tab 与 Home 按钮。
- Garfish 完整加载并渲染子应用内容到指定容器。

**Non-Goals:**
- 子应用生命周期高级编排（灰度、权限隔离等）。
- 远程配置中心或后端持久化。
- 子应用运行时性能监控与埋点。

## Decisions

1. **采用 Garfish 作为微前端框架**
   - 选择原因：与需求匹配、生态成熟、支持基于路由的子应用加载。
   - 备选方案：single-spa 或 qiankun；因与既有技术栈和团队认知偏差较大而不选。

2. **父容器 UI 使用 React + 简易 UI 组件**
   - 选择原因：与仓库现有技术栈保持一致、可快速实现。
   - 备选方案：引入完整设计系统；为降低依赖和开发成本而暂不引入。

3. **子应用配置存储为本地持久化**
   - 选择原因：无需后端配合，便于本地与演示场景。
   - 备选方案：接入后端配置服务；因需求未要求而暂缓。

4. **导航结构：卡片式主页 + 子应用 Tab**
   - 选择原因：主页以卡片网格展示子应用，像浏览器书签一样直观；进入子应用后才显示 Tab 与 Home，导航层次清晰。
   - 备选方案：列表式导航；但卡片更直观、可扩展性更好（可添加图标、描述等）。

## Risks / Trade-offs

- [子应用配置字段不够] → 当前最小字段为 name/url，必要时再扩展但保持 UI 简洁。
- [本地存储丢失/不同步] → 允许导入/导出配置作为后续扩展。
- [路由冲突] → 对 `activeRule` 做基本校验并在 UI 提示。

## Migration Plan

- 在仓库根目录新增父容器应用目录与基础路由。
- 集成 Garfish 并实现子应用注册逻辑。
- 增加设置页与本地存储。
- 增加顶部导航与 Home 交互。
- 如需回滚，删除新增应用目录与相关依赖即可。
